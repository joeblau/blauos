# Public inputs for the native XNU security interfaces

The source audit found no verified matching public header set for Apple XNU `xnu-12377.121.6` (`ac9718fb1af618d5ce8678d0dc6e8a58f252216f`). This is a bounded finding about the inspected public releases and repositories. It does not establish that these inputs are absent from Apple’s internal distributions or an uninspected Kernel Debug Kit. No new dependency, source pin, compatibility stub or security bypass was added.

The structured [research receipt](../../evidence/native/security-inputs.json) binds the exact Git trees, catalog blob/content hashes, path counts, inspected file hashes and compatibility limits. It records research completion separately from native build and physical boot acceptance.

Apple’s [macOS 26.5 source catalog](https://github.com/apple-oss-distributions/distribution-macOS/blob/83390100289cedfe669c31a96c94326d31afa1ed/release.json) contains 171 projects and pins this exact XNU revision. Its matching Security release is `Security-61901.120.67`, revision `97c3a4296c1ea06b0fe1877a7e616aa84450b5b2`. The complete, nontruncated 17,364-entry [Security tree](https://github.com/apple-oss-distributions/Security/tree/97c3a4296c1ea06b0fe1877a7e616aa84450b5b2) contains neither missing header family. The catalog supplies no standalone TrustCache or CoreEntitlements project. The inspected public repository catalogs likewise supplied no separate project under either name.

The pinned XNU tree contains 6,510 entries and publishes 12 [legacy CoreEntitlements headers](https://github.com/apple-oss-distributions/xnu/tree/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/EXTERNAL_HEADERS/CoreEntitlements). It does not contain `TrustCache/API.h`, `CoreEntitlements/V2/API.h` or `CoreEntitlements/V2/Kernel.h` under `EXTERNAL_HEADERS`. The two V2 paths also have no returned commits in the public XNU path histories.

All inspected recursive API trees reported `truncated: false`. The XNU entry count was also checked against its local pinned Git tree. Git tree object IDs and the exact API replay URLs are in the receipt. Counts include directory entries, rather than only source files. The four [published PCC snapshots](https://github.com/apple/security-pcc/commits/e3b4584d3caeb0b4244728a01fca50405101b42c/) contain selected PCC components, with no XNU source tree or matching API headers. Apple’s [software foundations guide](https://security.apple.com/documentation/private-cloud-compute/softwarefoundations) describes the hardened operating system and trust-cache enforcement; this architectural documentation does not supply the missing C headers or implementation.

There is a genuine historical TrustCache input to investigate. XNU `8796.101.5`, revision `aca3beaa3dfbd42498b42c5e5ce20a938e6554e5`, publishes five [TrustCache headers](https://github.com/apple-oss-distributions/xnu/tree/aca3beaa3dfbd42498b42c5e5ce20a938e6554e5/EXTERNAL_HEADERS/TrustCache): API, raw types, return codes, runtime types and type configuration. The public path first appears in `8792.41.9`; [XNU 10002.1.13](https://github.com/apple-oss-distributions/xnu/commit/1031c584a5e37aff177559b9f69dbd3c8c3fd30a) removes all five headers. Their exact Git blob IDs and SHA256 hashes are preserved in the receipt.

Those older headers cover every TC identifier name used by the selected current trust-cache consumers. That lexical comparison does not verify the runtime structures or implementation. The actual [AMFI callback interface](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/libkern/libkern/amfi/amfi.h) advances from TrustCache version 3 to 4, inserting `queryGetUUID` before the version-3 callbacks. The older API does not declare its corresponding query function. Historical headers are therefore a candidate for an isolated compile/ABI investigation, not a verified matching input set. No such compile experiment was performed in this research.

CoreEntitlements V2 needs concrete layouts. The [current native code](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/vm/pmap_cs.h) embeds `CEContext_t` by value in provisioning-profile structures. Its [PPL implementation](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/arm/pmap/pmap.c) allocates context, element and buffer objects and invokes V2 callbacks. Legacy `CEQueryContext_t` is a different published API. An opaque forward declaration or renamed legacy header cannot demonstrate compatible object sizes, callback tables or semantics.

Apple’s [pinned external build instructions](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/README.md) require a matching KDK for Apple Silicon and pass `KDKROOT` to the build. The [make rules](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/makedefs/MakeInc.def) add KDK private headers and `KernelSupport` to include paths and force-load its platform support archive. This is the documented candidate input route to verify. The contents of a matching macOS 26.5 kit, including the exact missing headers and archive, remain **unverified**. The current macOS 27.2 build host is not a validated match; no proprietary SDK or KDK was downloaded.

The local failed native attempts are recorded in the [native kernel audit](native-kernel-build.md). They prove that the available local inputs are incomplete. This separate source audit explains which public alternatives were checked and why none currently establishes the modern native build closure.
